> 在 GPU0 上做这 5 个实验；结果出来后要判断和预期是否一致，不一致时说明怎么处理。插件重装为 0.1.7（只新增默认关闭的 `VTS_STEP_TRACE`）。
> 脚本：`experiments/w6/run_followups2.sh`（阶段 t1–t5 依次运行；一个阶段失败会记录下来，后面继续；每个服务启动前检查 GPU0 上没有别的进程）。

## 统一的"不一致时怎么处理"

每个实验都按下面的顺序处理，不临时改判据：

1. **先排除测量问题**：追踪是否覆盖了整个测量窗口、重复之间是否一致、对照组是否复现了以前的数（每个实验都带一个复现点）。测量有问题就修好重跑，不判定。
2. **测量可信时，按判据如实记为"成立 / 证伪"**，写进结果文档，并改写受影响的已有结论（例如 FOLLOWUP_RESULTS 里那条推断）。
3. **不追加事后解释去"挽救"预测**。如果需要新解释，写成新的待验证假设，附上下一步最小实验和成本；本轮内不追加运行，除非成本 ≤ 30 分钟且另经确认。

## T1：B0 并发越高越慢的原因（S4 的后续）

**已知**：B0、P 负载、预算 2048，并发 32 → 96 吞吐降 6–8%；运行中的请求数不变（17 / 21），不是重复编码，没有抢占。读源码确认：等待队列的循环在预算用完时就停止，不会每步扫描整个队列（`scheduler.py` 约 915–925 行）。所以"调度器扫描等待队列"这条备选解释不成立。

**设置**：B0，P 负载，预算 2048，并发 {32, 64, 96}，2 次重复，两个模型；打开 `VTS_STEP_TRACE`（每一步记录：整步耗时、`schedule()` 耗时、`update_from_output()` 耗时、这一步里 Python 垃圾回收的耗时、排队数、运行数、本步调度的 token 数）。

**分解**：吞吐 ∝ 每步 token 数 n ÷ 每步耗时 w（每个请求的 token 数不变）。把并发 32 → 96 时 ln(吞吐) 的变化拆成三部分：
- (i) 每步 token 数变少：Δln n；
- (ii) CPU 开销变大：调度 + 输出处理 + 垃圾回收的耗时增量对 Δln w 的贡献；
- (iii) 其余部分（GPU 执行等）变慢：剩下的那部分 Δln w。

| 假设 | 判据 | 预测 |
|---|---|---|
| **H-T1a** 吞吐下降可以被上面三部分之一解释 | 某一部分占 Δln(吞吐) 的 ≥ 50%（每个模型，2 次平均） | (ii) CPU 开销，可能来自等待请求变多后垃圾回收变慢（推测，把握不大） |
| H-T1b 追踪本身不改变现象 | 带追踪时，并发 96 的吞吐仍比并发 32 低 ≥ 3% | 成立 |

H-T1a 不成立（没有一部分 ≥ 50%）时，结论写成"引擎内部的三部分都解释不了，问题可能在引擎外（API 进程或进程间通信）"，并给出下一步实验，不在本轮追加。

## T2：FP8 的 ViT 为什么单请求时慢、serving 时快

**已知**：单请求分阶段计时（`stage_bench.py`，进程内引擎）里，FP8 的 ViT 比 bf16 慢 10–69%；serving 并发 64 时，每次 ViT 调用只有 2–2.5 张图，FP8 的 ViT 每张图反而快 7–10%。两者有两个不同：引擎形态（进程内对多进程服务）和并发（1 对 64）。

**设置**：serving，并发 1，打开 ViT 追踪；B0 × {bf16，全量 FP8}；P 负载（4 张图）和 D 负载（1 张图）；两个模型；1 次。

| 假设 | 判据 | 读法 |
|---|---|---|
| **H-T2** 单请求时的变慢是进程内计时环境造成的 | serving 并发 1 时，FP8 每张图的 ViT 时间 ≤ bf16 的 1.05 倍（P 和 D、两个模型，4 格） | 成立 → 引擎形态是原因（推测是进程内 CPU 争用让 FP8 多出的 kernel 启动更贵）；证伪 → 并发 / 批组成才是原因 |

## T3：Qwen3.5 上 Amdahl 还差 0.04

**已知**：S2 的追踪里，FP8（只量化 LLM）对非 ViT 部分的加速，Qwen3.5 在 B0 上是 1.66 倍、在 RATE 配置上只有 1.51 倍（比值 0.91）；Qwen3-VL 两者相同（1.52 对 1.52）。B0 每个请求 3180 个 prompt token，RATE 是 1612。

**设置**：纯文本 prefill 扫描（`prefill_sweep.py`，单请求，前缀缓存开，和 serving 默认一致），长度 {1612, 3180}，bf16 对只量化 LLM 的 FP8，两个模型，10 次中位数。

| 假设 | 判据 | 读法 |
|---|---|---|
| **H-T3** 差距来自 FP8 的加速随 prefill 长度变化 | Qwen3.5：加速(1612) ÷ 加速(3180) ≤ 0.95；Qwen3-VL：这个比值 ≥ 0.97 | 成立 → 短序列上 FP8 加速更小，且只在 Qwen3.5 上明显；证伪 → 原因不在 prefill，可能在 decode 或调度 |

## T4：进程历史效应的具体来源

**已知**：Qwen3.5，前缀缓存开时，先跑过 4 图请求的进程，单图 prefill 慢约 14 ms；关掉缓存就消失（S3）。vLLM 0.32 的 Mamba 缓存模式只有 align 和 none 两种，开前缀缓存时必须用 align，所以不能在开着缓存的情况下单独换模式。改用 `LLM.reset_prefix_cache()`：在 P 和 D 之间清空前缀缓存，看效应还在不在。

**设置**：Qwen3.5 B0，前缀缓存开，单请求 20 次中位数，各 2 个进程：只跑 D、先 P 后 D、先 P 后清空缓存再 D。

| 假设 | 判据 | 读法 |
|---|---|---|
| H-T4a 阳性对照 | 先 P 后 D 比只跑 D 慢 ≥ 8 ms | 不复现则不判 T4b |
| **H-T4b** 效应来自缓存里留下的内容 | 先 P、清空缓存、再 D 和只跑 D 相差 ≤ 3 ms | 成立 → 来自缓存中的块；证伪（仍 ≥ 8 ms）→ 来自 align 模式下缓存以外的状态 |

## T5：S1b 里 Qwen3.5 降分辨率为什么比预测低 6%

**已知（事后观察，不能当证据）**：Qwen3.5 按 528 个 token 一块分配 KV。vLLM 准入时只要求当前已有的 token 装得下（`scheduler_reserve_full_isl`，默认开，见 `kv_cache_manager.py` 约 522 行），生成过程中跨到下一个块时，如果没有空闲块就要抢占。已有数据里，生成中跨块的配置抢占次数都很多（S1b 降分辨率 183、S1a 两种方法 341 / 397、W4 K1 压缩配置 287–311），不跨块的很少（S1b 裁剪 30、B0 15–29）。FOLLOWUP_RESULTS §1 原来的推断（"平均占用越过块边界"）只能解释 1–2%，不够。

**设置**：Qwen3.5 B0，K1 设置（4 GiB KV、2 张 896 图、并发 128），只改输出长度：456 和 480 个 token，3 次重复。prompt 1648：输出 456 时最长 2104，不跨 2112；输出 480 时最后 16 个 token 跨块。按平均占用算的记账模型预测两者的运行并发之比约 0.995。

| 假设 | 判据 | 读法 |
|---|---|---|
| **H-T5** 跨块边界导致抢占、拉低运行并发 | 输出 480 的抢占次数 ≥ 输出 456 的 3 倍，且运行并发低 ≥ 3%（3 次平均） | 成立 → 记账模型要加一项"生成中跨块的抢占"；证伪 → S1b 的 6% 仍未解释，原推断撤回 |
