# W4 预注册方案：serving 收益拆解

> 2026-10-21 起草，**审阅通过后才启动**。启动后，本文件里的预测值和判据不再修改；如果要改，在文末"变更记录"里写明原因和时间。
> 前置：W3 精度扫描（`docs/results/W3_RESULTS.md`）；W1 serving 基线（`docs/results/W1_RESULTS.md`）。

## 0. 一句话

**W4 要回答：token 裁剪在 serving 上，有没有降分辨率给不了的收益？混合注意力（Qwen3.5）又怎么改变压缩换来的 KV / 并发收益？**

W3 的结论是：精度上，降分辨率是最强的基线；只有 TextVQA 这类场景，修正版 RATE 更好。降分辨率同时减少 ViT 和 LLM 的计算量；裁剪要先把完整的 ViT 跑完，再加上选择开销，只省 LLM 这一侧。所以 W4 的结果无论偏向哪边，都能如实讲出来。

## 1. 已确认的决定（2026-10-21）

## 3. 实验 ①：分阶段开销微基准（先做，约 1 GPU·时）

| 项 | 内容 |
|---|---|
| 做法 | vLLM 引擎在同一进程里跑（`VLLM_ENABLE_V1_MULTIPROCESSING=0`），一次只发 1 个请求。用 CUDA event 和同步分别计时：ViT 前向、插件的选择函数、首 token 延迟（prefill，`max_tokens=1`）、每输出 token 耗时（TPOT，`max_tokens=129`）。预热 3 次，再测 20 次，取中位数 |
| 负载 | P 形（4 张图，文本约 50 token）和 D 形（1 张图） |
| 配置 | 2 个模型 × 5 种方法（保留 50%） |
| 输出 | 每个配置下 ViT 占 TTFT 的比例、选择开销占 TTFT 的比例、LLM prefill 时间 |
| 注意 | 计时插入的同步会让绝对时间偏大一点，所以只用来拆比例，不和 ③ 的吞吐直接比较 |

**两段式预注册**：① 跑完后、③ 开始之前，用 ① 的阶段耗时算出 ③ 在饱和时的吞吐预测，把数字补进本文件 §5 的空格里（这是唯一允许的补写）。算法是：饱和吞吐 ∝ 1 / 单请求的 GPU 时间（ViT + 选择 + LLM prefill + 32 个 decode 步）。

## 4. 实验 ②：K1 显存紧张负载（"那一个发现"）

### 4.1 负载

| 项 | 设置 | 理由 |
|---|---|---|
| 每个请求 | 2 张 896×896 图（B0 时 1568 个视觉 token），文本约 50 token，输出 256 token（ignore-eos） | 视觉 token 占 KV 的大头；输出够长，KV 会在 decode 时持续增长 |
| KV 预算 | 两个模型用**相同的字节数**：`--kv-cache-memory-bytes`，起始值 4 GiB；K1 单独设 `--max-model-len 4096` | 模拟"显存紧张"（小卡、多模型共卡）；用同样的字节数，比较才公平。max-model-len 调小，是因为 vLLM 要求 KV 池至少装得下一个最长请求（2 GiB 时 Qwen3-VL 只能装约 1.45 万个 token） |
| 发压方式 | 闭环并发 {32, 64, 128, 256}，每个点 4 × 并发数个请求（至少 256 个），各 3 次 | 要让每种配置都受 KV 限制，所以并发比 W1 高 |
| 主要指标 | **稳态运行并发** = 稳态期间（去掉前 20% 和后 10% 的时间）`vllm:num_requests_running` 的平均值；每 1 秒从 `/metrics` 采样一次 | 直接反映准入并发 |
| 次要指标 | 吞吐（req/s、输出 tok/s）、`vllm:kv_cache_usage_perc`、`vllm:num_preemptions`、TTFT / TPOT | — |
| 点数 | 5 种方法 × 2 个模型 × 4 档并发 × 3 次 = 120 | 约 3.5 GPU·时 |

### 4.2 标定（只用 B0，在正式运行之前）

| 步骤 | 判据 | 不满足时怎么办 |
|---|---|---|
| 1. 用 4 GiB 预算、并发 128 跑两个模型的 B0 | 两个模型的稳态 KV 占用都 ≥ 85%，而且有请求在排队（waiting > 0） | 预算改成 3 GiB，再不行就 2 GiB；最终取值写进变更记录 |
| 2. 实测 Qwen3.5 每组状态实际占几个物理块（m） | 每个请求占的块数 = KV 占用 × 总块数 ÷ 运行中的请求数；m =（每个请求的块数 − 注意力块数）÷ 3 | m 不在 [1, 2] 里时，照实记录，用实测值算预测 |
| 3. 实测提示词长度 | 从 B0 的 usage 里取实际的 prompt token 数 | 用实测值替换下表里的 50 |

标定只用 B0 的数据，压缩配置一次都不跑，所以用标定得到的 m 和提示词长度去算预测值，不算"偷看结果"。

### 4.3 预测（`experiments/w4/k1_predict.py`，2026-10-21 锁定）

模型：稳态运行并发 ∝ 1 / 每个请求在 decode 期间的平均 KV 占用。

- 全注意力：⌈token 数 / 16⌉ 个块，每 token 144 KiB；
- 混合：⌈token 数 / 528⌉ 个注意力块，加 3 × m 个状态块（3 组 GDN）。

依据：vLLM 0.32 日志中的 `kv cache group sizes (528, 528, 528, 528)`、`Mamba cache mode is set to 'align'`；源码 `single_type_kv_cache_manager.py:1676-1778`，align 模式下每组状态的物理块数上限是 1 + 部分命中 + 检查点。

| 方法（保留 50%） | 视觉 token | 全注意力 Qwen3-VL：预测并发增益 | 混合 Qwen3.5：m = 1 | 混合 Qwen3.5：m = 2 |
|---|---|---|---|---|
| B0 | 1568 | 1.00 | 1.00 | 1.00 |
| 降分辨率（每张图缩到 640×640） | 800 | **1.78** | **1.35** | **1.22** |
| 裁剪（随机 / RATE / DivPrune 都一样） | 784 | **1.81** | **1.36** | **1.23** |

敏感性：文本 80 token 时是 1.78 / 1.33 / 1.21；输出 512 token 时是 1.71 / 1.26 / 1.17。两种结构之间的差距一直在 0.4 以上。

**标定后锁定（2026-10-22 00:2x，只用了 B0 的标定数据，压缩配置一次都还没跑）**：实测 prompt 长度 1644（Qwen3-VL）/ 1648（Qwen3.5），实测 m = 1.04，取 m = 1。

| 方法（保留 50%） | Qwen3-VL-4B 预测增益 | Qwen3.5-4B 预测增益 |
|---|---|---|
| 裁剪（随机 / RATE / DivPrune） | **1.79** | **1.33** |
| 降分辨率 | **1.76** | **1.32** |

H-K1 的预测相对差距 =（1.79 − 1.33）÷ 1.79 = 26%，远大于证伪阈值 10%。

### 4.4 假设与判据（锁定）

| 编号 | 假设 | 主指标 | 什么结果算证伪 / 不支持 |
|---|---|---|---|
| **H-K1** | 压缩换来的准入并发增益，全注意力明显大于混合 | 并发 128 时，裁剪（三种方法的中位数）的稳态运行并发增益 | （全注意力增益 − 混合增益）÷ 全注意力增益 ≤ 10%，就算证伪 |
| H-K3 | 实测增益和 §4.3 的预测一致 | 实测 ÷ 预测 | 在 0.85–1.15 之间算"账本模型可用"；超出就照实报告偏差方向，再分析原因（例如块粒度、抢占、准入策略） |
| H-K1b | 同样的 token 数下，裁剪和降分辨率的 KV 增益相同 | 两者的增益之比 | 相差超过 10%，说明还有别的机制（例如 ViT 的显存峰值影响了准入） |
| H-K4 | 在 K1 下，选择方法（随机 / RATE / DivPrune）对并发增益没有影响 | 三者之间的差别 | 差别超过 10% |

## 5. 实验 ③：P 负载（计算受限）

| 项 | 设置 |
|---|---|
| 负载 | 同 W1 的 P：每个请求 4 张 896×896 图，文本约 50 token，输出 32 token |
| 每步 token 预算 | 2048（L40 默认值）和 8192（`--max-num-batched-tokens 8192`） |
| 并发 | {1, 8, 32, 64} |
| 点数 | 5 种方法 × 2 个模型 × 2 档预算 × 4 档并发 × 3 次 = 240，约 7 GPU·时 |
| 指标 | req/s、prompt tok/s、TTFT p50 / p99、TPOT p50；GPU SM% 和 CPU 探针 |

| 编号 | 假设 | 预测 | 什么结果算证伪 |
|---|---|---|---|
| H-P1 | 饱和吞吐（并发 64）的增益：降分辨率 > 裁剪 | **① 跑完后补写（2026-10-22，③ 还没跑）**。按 §3 预先定好的算法（ViT + 选择 + LLM prefill + 32 个 decode 步）：Qwen3-VL 上降分辨率 **1.36×**，随机 1.21×、RATE 1.21×、DivPrune 1.05×；Qwen3.5 上降分辨率 **1.32×**，随机 1.20×、RATE 1.19×、DivPrune 1.04×。另外补一个上界（只算 ViT + 选择 + prefill，因为饱和时 decode 是批处理的，按 32 步全算会低估增益）：Qwen3-VL 2.22 / 1.55 / 1.52 / 1.14×；Qwen3.5 2.02 / 1.49 / 1.47 / 1.11×。预计实测落在这两者之间 | 裁剪的增益 ≥ 降分辨率的增益 |
| H-P2 | 裁剪方法之间：随机 ≥ RATE ≥ DivPrune（选择开销越大，吞吐越低） | 差距等于 ① 测得的选择开销所占的比例（① 的结果：4 张图时随机 0.9 ms、RATE 3.9–4.0 ms、DivPrune 99.8–100.6 ms） | 顺序颠倒，而且差别超过重复间的极差 |
| H-K0 | P 负载不受 KV 限制，所以两种结构的压缩增益相近 | 两种结构的增益相差 ≤ 10% | 相差超过 10% |
| H-P3 | 预算 8192 比 2048 的饱和吞吐更高（每步塞得更满） | 方向性预测 | 8192 不高于 2048 |

## 9b. 实验 ⑥：prefill 长度扫描（2026-10-22 新增，探索性）

| 项 | 内容 |
|---|---|
| 起因 | ① 里 Qwen3.5 的 D 形 prefill（822 token）要 106 ms，Qwen3-VL 只要 60 ms（慢约 77%），P 形（3180 token）却只慢 7% |
| 两种备选解释 | (a) GDN 层的 prefill 有和长度无关的固定开销；(b) 开着前缀缓存时，Mamba 的 align 模式要在块边界写检查点，带来额外开销 |
| 做法 | 单请求，纯文本 prompt（随机 token id，每次都不同，避免缓存命中），长度 {128, 256, 512, 822, 1024, 2048, 3180, 4096, 8192}；两个模型 × 前缀缓存开 / 关；预热 3 次、测 10 次，取 TTFT 中位数 |
| 判读 | 关掉前缀缓存后，Qwen3.5 的短序列额外开销基本消失 → 支持 (b)；不变 → 支持 (a)；两个模型的差值随长度近似不变 → 固定开销 |
| 时间 | K1 之后，GPU0 约 30 分钟 |
| 性质 | **探索性**，和 K1 一起推进，不进入预注册的假设检验 |
