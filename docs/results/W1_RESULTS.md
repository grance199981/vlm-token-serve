# W1 结果：不压缩（B0）时的精度与 serving 基线

> 2026-10-20 整理。所有数字都来自实测。
> - 表格由 `experiments/w1/summarize_accuracy.py`、`summarize_serving.py`、`bottleneck_probe.py` 生成

## 1. 实验设置

| 项 | 精度评测 | serving 评测 |
|---|---|---|
| 硬件 | 2×L40 48GB 服务器的 GPU0，独占 | 同左，每个服务启动前都检查过卡上没有其他进程 |
| 软件 | vLLM 0.32.0、torch 2.13.0（cu13.0）、transformers 5.19.0、lmms-eval 0.7.3 | 同左 |
| 模型 | Qwen3-VL-4B-Instruct、Qwen3.5-4B，均为 BF16 | 同左 |
| 服务参数 | gpu-memory-utilization 0.90、max-model-len 32768、max-num-seqs 64、图像尺寸用模型默认值 | gpu-memory-utilization 0.90、max-model-len 16384，其余用 vLLM 默认值 |
| 调度默认值（L40 显存 < 70 GiB 那一档） | — | 每步 token 预算 2048，最大序列数 256（`vllm/engine/arg_utils.py`） |
| 缓存 | 默认 | 默认开启 prefix caching 和 MM 预处理缓存；每个点用不同 seed，**每次服务结束时检查命中率，都是 0.0%** |
| 生成设置 | greedy，关闭思考模式，seed 0 | temperature 0，ignore-eos，关闭思考模式 |
| 负载 | 5 个任务全量 | P = 每个请求 4 张 896² 随机图 + 64 个文本 token，输出 32；D = 每个请求 1 张图，输出 512 |
| 重复次数 | 1 | 并发 {1, 4, 8, 16, 32, 64} × 3 次，两个模型交替跑 |

## 2. 精度基线

| 任务（指标） | Qwen3-VL-4B（95% CI） | Qwen3.5-4B（95% CI） | 官方参照 | 可比性 |
|---|---|---|---|---|
| ChartQA test（relaxed acc） | 84.04 [82.68, 85.48] | 85.28 [84.00, 86.64] | 模型卡没有 | — |
| TextVQA val（exact match） | 80.50 [79.47, 81.51] | 82.53 [81.62, 83.46] | 模型卡没有 | — |
| DocVQA val（ANLS） | 94.75 [94.21, 95.27] | 95.56 [95.06, 96.05] | Qwen3-VL-4B：95.3（test 集） | 集合不同（val 对 test），差 0.55 |
| MME（感知 / 认知） | 1705.5 / 615.0 | 1700.0 / 624.3 | 模型卡没有 | — |

CI 是对逐条样本做 bootstrap（2000 次，seed 0）得到的。MME 和 MMBench 是汇总指标，没有算 CI。

## 5. 结论

| # | 结论 | 证据 | 状态 |
|---|---|---|---|
| 1 | Qwen3-VL-4B 的精度基线和官方一致，W0 担心的"共用预处理有问题"没有依据 | DocVQA 相差 0.55（val 对 test） | **已确认**（只有一个可以直接比的任务） |
| 2 | Qwen3.5-4B 在 MMBench 上的 76.46 分偏低，原因是答题格式 | 13.7% 的回答不以选项字母开头 | **已确认**；这个分数只能和它自己比 |
| 3 | P 负载的吞吐平台（约 2 req/s）是在服务端被 prefill 卡住的 | 有排队；KV ≤ 32%；API server CPU ≤ 47%；SM 约 100% | **已确认**"不是 KV、不是前端"；"受算力限制"属于**推断** |
| 4 | 这个平台有一部分可能是调度参数造成的，而不是硬件上限 | 每步 token 预算 2048，一个 P 请求约 3200 token，至少要切 2 段 | **待验证**（W4 扫 2048 / 8192 两档） |
| 5 | 在 W1 的两类负载下，KV 从来不是瓶颈 | 整轮最高 KV 占用：41.3% / 21.4% | **已确认** |
| 6 | 所以两种结构在 W1 负载下表现几乎一样 | 同一并发下的 req/s 相差 ≤ 10% | **已确认** |
| 7 | P 负载下 decode 被大段 prefill 拖慢 | 并发 1 → 64，TPOT p50 从 12.8 涨到 328 ms（Qwen3-VL）/ 244 ms（Qwen3.5） | **已确认**现象；机制（chunked prefill 混排）属于**推断** |
| 8 | 单请求 decode 接近 roofline 预测的下限 | D 负载并发 1 时 TPOT 12.3–12.6 ms，推算下限约 11 ms | **推断**（L40 规格还没核对） |
| 9 | 在 merger 之后裁剪视觉 token，P 负载的收益上限受 ViT 占比限制 | 按 FLOPs 粗算 ViT 约占 28%，Amdahl 上限约 2.2 倍（裁掉 75%） | **推断**，W4 用 profiler 测 |

## 6. 测量中发现并处理的问题

| 问题 | 怎么发现的 | 影响 | 处理 |
|---|---|---|---|
| 不同压测点之间缓存命中 | P 负载曲线不单调：并发 4 吞吐 4.6 req/s，并发 8 只有 1.9 req/s | 第一轮 serving 全部作废（D 负载也偏高：并发 64 时 3.4 对 2.9 req/s） | 每个点用不同 seed、单独预热、检查命中率；第一轮保留作负对照（命中率 55.3%） |
| `ps %cpu` 给的是生命周期平均值 | 读数随时间单调下降 | CPU 探针无效 | 改用 `/proc` 增量；用忙循环（99%）和 sleep（0%）做正负对照 |
| 抽查脚本把字符串当成列表来索引 | 回答"只有首字母" | 差点误判 ChartQA 分数无效 | 修正，确认 0.725 有效 |
| 汇总脚本把 `submissions/` 目录当成了一个模型 | 报 KeyError | 无 | 跳过没有 results 字段的文件 |

## 7. 对 W4 的影响

| 负载 | W1 告诉我们什么 | W4 要做的 |
|---|---|---|
| P | 受 prefill 限制；ViT 占比决定裁剪收益的上限 | 检验 H2（降分辨率对比 merger 之后裁剪）；扫每步 token 预算 2048 / 8192 |
| D | 不受 KV 限制，decode 接近 roofline | 当负对照：预期压缩几乎没有收益 |
| K1（新）显存紧张 | W1 负载下 KV 不会成为瓶颈 | 压低 KV 预算，让 KV 成为瓶颈，检验 H1 |
| K2（新）多轮会话 | 同上 | 图片留在上下文里，看压缩换来的前缀缓存容量（需要自己写带图的客户端） |
