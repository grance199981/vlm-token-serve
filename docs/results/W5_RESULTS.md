# W5 结果：Triton DivPrune 算子 + FP8 权重与 token 压缩的叠加（2026-10-24 完成）

在 2×L40 48GB 服务器上运行（插件 0.1.5，GPU0，服务器时间 06:30–15:13），9 个阶段全部 rc=0：serving 全部请求成功、缓存命中 0%，精度配置全部 valid=yes，运行期间 GPU0 干扰监控没有报警（中间有两次 SSH 查询超时，那两次没查到）。方案和预注册判据见 `docs/plans/W5_PLAN.md`。

## 0. 一句话

- **(a)** 把 DivPrune 的贪心选择写成一个 Triton kernel 后，每张图从约 25 ms 降到 0.42 ms（61×），选出的 token 集合不变；DivPrune 在计算受限负载上的吞吐增益从 1.28× 升到 1.57–1.58×，**和随机选择一样**。这直接证实了 W4 的判断：DivPrune 吞吐低完全是选择开销造成的。
- **(b)** FP8 权重几乎不掉精度（OCR 平均 +0.0），单独就有 1.45–1.56× 的吞吐增益；和降分辨率叠加后达到 **3.05–3.06×**，是本项目所有配置里最高的。但**和裁剪叠加时收益明显小于相乘**（Qwen3.5 RATE：0.84）。
- **(c) 对照（§3）**：让 FP8 跳过 ViT 后，单请求时 ViT 不再变慢，单张图请求的 TTFT 降 13–15%；但**饱和吞吐下裁剪配置一点也没变快**（0.98× / 1.00×），不压缩的配置反而慢 3.5–4.5%。所以"ViT 在 FP8 下变慢"只解释单请求延迟，**不解释**裁剪 + FP8 吞吐小于相乘，原先的这个推断被否定了。

### 1.6 结论

1. DivPrune 的选择从约 25 ms/图 降到 0.42 ms/图（61×），选出的集合不变（Jaccard 1.000，GPU 上 60 项正确性测试通过，含贪心证书和负对照）。
2. 这是一次干预实验：只换选择的实现，DivPrune 的吞吐增益就从 1.28× 变成和随机一样（1.58× / 1.57×），TPOT 的额外拖累也和随机一样。W4 里"DivPrune 吞吐最低是选择开销造成的"从推断变成了实测。
3. 所以 W4 的发现 3（"选择算法开销不能忽略"）要加限定：**按官方算法逐步实现时**开销不能忽略；写成一个 kernel 后可以忽略，DivPrune 和随机、RATE 在吞吐上没有区别，选哪种方法只看精度。
4. 边界：N > 4096 退回 PyTorch（S 需要 N² × 4 字节）；只测了 L40；kernel 是单个 program 串行做完所有步，N 很大时 GEMM 成为主要部分，没有再优化。

|---|---|---|---|

### 2.5 结论

1. **FP8 权重在这两个 4B 模型上几乎免费**：OCR 平均不掉分，吞吐 1.45–1.56×（计算受限）/ 1.27–1.29×（decode 受限），单请求 TPOT 降 26–30%。
2. **精度损失严格相加**（残差 ≤ 0.45 分），所以"FP8 + 某种 token 压缩"的精度可以直接用两者各自的结果估计。
3. **吞吐收益在 decode 受限时几乎相乘（R 0.96–1.01），在计算受限时取决于压缩方式**：降分辨率接近相乘（R 0.94–1.02），裁剪明显小于相乘（R 0.84–0.92）。原先的推断是"FP8 把 ViT 也量化、ViT 反而变慢，而裁剪省不掉 ViT"。**§3 的对照否定了这个推断**：让 ViT 保持 bf16 后，裁剪配置的饱和吞吐没有变化。剩下的备选解释是 Amdahl 比例：FP8 只加速 LLM 部分，裁剪后 ViT 的占比更大，FP8 对裁剪配置的加速比自然更小。这一点和 H-V3 成立一致，但没有单独验证。
4. 实用结论：在这套设置下，**FP8 + 降分辨率 50% 是吞吐最高的配置（3.05× / 3.06×），精度和单独降分辨率一样（OCR 平均 −2.6 / −2.0）**。
5. 让 FP8 跳过视觉编码器的效果见 §3：单请求延迟变好，饱和吞吐变差或不变，不是无条件更好的选择。
6. 边界：只测了在线 FP8（per-tensor 权重、动态激活），没有测官方离线 FP8 权重；合成噪声图、一种图片尺寸、保留 50% 一档、4B 模型、L40。

## 3. W5c：FP8 只量化语言模型（ViT 保持 bf16）的对照

运行时 （插件 0.1.5，GPU0，服务器时间 19:20–22:34），3 个阶段全部 rc=0：48 个服务 0 失败、缓存命中 0%，干扰监控无报警。方案和预注册假设见 `docs/plans/W5_PLAN.md` §5（写于运行之前）。

**设置核对**：只量化 LLM 用 `--quantization fp8_per_tensor --quantization-config '{"ignore": ["visual.*"]}'`。被量化的层数：Qwen3-VL 144（全量 FP8 是 248），Qwen3.5 152（全量 250），全部是语言模型的层；量化方式（`fp8_per_tensor_static`）和 kernel（`CutlassFP8ScaledMMLinearKernel`）都和全量 FP8 相同。同一轮重跑的全量 FP8 复现了 W5 b2：Qwen3-VL B0 增益 1.441×（b2 1.450×），RATE 的 R 0.918（b2 0.919）；Qwen3.5 0.830（b2 0.840）。

### 3.4 按预注册判据（W5_PLAN §5）

| 假设 | 判据 | 实测 | 结论 |
|---|---|---|---|
| **H-V1** ViT 不再变慢 | ViT 在同一轮 bf16 的 ±5% 以内 | +2.9%、−6.8%、−0.2%、−3.2% | **一格不符**（Qwen3-VL 单张图快了 6.8%，约 2 ms；方向是更快） |

| **H-V5** 精度不变 | ChartQA \|Δ\| ≤ 1.0 | −0.7 / −0.3 | **成立** |

### 3.5 结论

1. **"ViT 在 FP8 下变慢"只在单请求时成立，在饱和吞吐下不成立。** 单请求时让 ViT 保持 bf16，ViT 和单张图 TTFT 都变好（TTFT −15% / −13%）；但并发 64 时，ViT 保持 bf16 反而让不压缩的配置慢 3.5–4.5%，裁剪配置不变（0.98× / 1.00×）。合理推断（未验证）：serving 时一次 ViT 调用里有多个请求的图片，矩阵更大，FP8 的动态激活量化开销被摊薄，FP8 ViT 在批处理下并不慢。
2. **所以 W5(b) 里裁剪 + FP8 吞吐小于相乘，不是因为 ViT 变慢。** Qwen3.5 上 R 从 0.83 到 0.87 的提高，主要来自分母（只量化 LLM 的 B0 变慢了），不是裁剪配置变快了（RATE 吞吐 1.003 倍）。按预注册的判读规则，H-V2 证伪、H-V3 成立，剩下的解释是 Amdahl 比例：FP8 只加速 LLM，裁剪后 ViT 的占比更大。这个解释和数据一致，但没有单独验证。
3. 实用结论：**是否让 FP8 跳过 ViT 取决于负载**。低并发、单张图、在意首字延迟时，跳过 ViT 更好；高并发、在意吞吐时，全量 FP8 更好（不压缩时快 3.5–4.5%，裁剪时没有差别）。精度上两者都不掉分（ChartQA 差 ≤ 0.7）。
4. 边界：只测了 P 负载（4 张 896×896 图）和单请求的两种形状；"批处理摊薄量化开销"是推断，没有测 serving 时每次 ViT 调用的批大小和耗时。
